## 운영 DB 적용 순서

기존 SQL이 적용되어 있다는 전제에서 다음 두 파일을 Supabase SQL Editor에서 순서대로 실행한다.

1. `supabase/migrations/202610300005_security_integrity.sql`
2. `supabase/migrations/202610300006_serialize_geometry.sql`

005는 기존 공동체 연결 오류나 순환 계층이 있으면 전체 롤백한다. 데이터를 자동 삭제하거나 임의로 옮기지 않는다. 실패하면 `supabase/checks/inventory_integrity.sql`로 원인을 먼저 확인한다.

이전에 준비한 `202610300004_community_member_management.sql`의 적용 여부도 별도로 확인해야 한다. 이번 보안 SQL과 별개로 대표의 강퇴 기능에 필요하다.

2026-10-31 사용자 확인: 005·006 SQL의 운영 Supabase 적용 완료. 이 에이전트가 운영 DB에 직접 접속해 재검증한 것은 아니며, 아래 실제 계정 QA는 별도로 확인한다.

## 자동 검증

초기 보안 개선 검증: `npm.cmd test` 6개 통과, `npm.cmd run lint` 통과, `npm.cmd run build` 통과(타입 검사 및 전체 페이지 생성 포함).

추가 높이 미리보기 점검: Three.js Mesh와 Box3로 바닥에서 60cm·자체 높이 80cm의 실제 경계가 60~140cm임을 검증했다. 이전 자체 높이 50cm는 좌표에 더해지지 않는다. 해당 회귀 테스트를 포함해 총 7개 테스트가 통과했다. 공유 배치 미리보기에 부모 공간 전체 높이의 외곽선을 추가하고, 아랫면·윗면·부모 높이·상단 여유를 함께 표시했다. 브라우저 접근 권한 제한으로 실제 로그인 화면에서의 시각 검증은 수행하지 못했다.

`npm.cmd test`는 메모리 PostgreSQL(PGlite)에 전체 마이그레이션을 순서대로 적용한다. 운영 데이터나 인증 정보는 사용하지 않는다.

- 다른 공동체 공간의 상위 연결·물건 연결·장면 연결 거부
- 자기 자신 및 내부 공간을 상위로 지정하는 요청 거부
- 다른 공동체 경로 스냅샷 조회 거부
- 정상 배치 및 내부 장면 치수 자동 동기화
- 형제 공간·창문 겹침 및 기존 배치보다 작은 크기 변경 거부
- 물건 일괄 이동과 공간 삭제, 이동 기록 1회 생성
- 실제 authenticated 역할의 다른 공동체 조회·수정 거부
- 자동 로그인 해제 쿠키, 로그아웃 쿠키 삭제 옵션 유지
- 요청보다 작은 서버 응답 제한에서도 목록 전체 수집
- 물건 수정의 선택적 캐시 무효화와 기록 무효화
- 같은 공동체 캐시 재사용, 다른 공동체 캐시 분리
- 취소된 조회의 추가 페이지 요청 중단

## 운영 적용 후 확인할 항목

평면 조작 추가 검증: 드래그 이동·네 모서리 크기 변경·부모 범위·주변 벽 스냅·역방향 다시 그리기를 검증하는 테스트 6개를 추가하여 총 13개가 통과했다. 타입 검사, 코드 검사, 배포용 빌드도 통과했다. 공간·벽·창문이 같은 조작을 사용하고, 숫자와 3D 미리보기가 드래그 중 갱신되도록 연결했다. 실제 마우스·터치 조작은 브라우저 접근 제한으로 별도 확인이 필요하다.

두 단계 편집 추가 검증: 크기 단계가 위치를 변경하지 않는지, 배치 단계가 크기를 변경하지 않는지, 잘못된 크기를 거부하고 단계 전환 시 유효한 위치를 유지하는지 확인하는 테스트 3개를 추가했다. 총 16개 테스트가 통과했다. 새 객체는 크기부터, 기존 객체 수정은 배치부터 시작하고, 다음 단계 이동은 DB 저장 없이 처리한다.

1. 같은 브라우저에서 A 계정 로그아웃 → B 계정 로그인. 공동체·기록·휴지통에 A 데이터가 잠깐이라도 나타나지 않는지 확인.
2. 자동 로그인을 끄고 로그인 → 토큰 갱신 → 브라우저 종료. 브라우저의 세션 복원 옵션을 끈 환경에서 로그인 상태가 유지되지 않는지 확인. 브라우저 자체의 세션 복원은 서비스가 제어하지 못한다.
3. 두 계정이 같은 빈 영역에 동시에 저장. 하나만 저장되고 다른 요청은 겹침 오류가 되는지 확인. 메모리 DB는 단일 연결이므로 실제 다중 연결 동시성은 별도 확인이 필요하다.
4. 창문·공간을 회전·확대하고 색상·치수를 수정. demand 렌더링에서 화면이 계속 따라오는지 확인.
5. 대표가 구성원 제외 후 상대 계정의 새 조회·수정 거부 확인. 이미 전달된 화면 데이터는 회수할 수 없으며, 오래된 데이터는 창 포커스 복귀·화면 재진입·명시적 새로고침으로 갱신된다.

캐시 staleTime은 60초다. 다른 사용자의 수정이 활성 화면에 즉시 전달되는 실시간 구독은 이번 작업에 추가하지 않았다. 전체 목록을 페이지로 모으므로 대규모 공동체에서는 추후 검색·화면별 서버 페이지 나누기가 필요하다.
