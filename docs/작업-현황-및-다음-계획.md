# 수납바구니 작업 현황 및 다음 계획

> 마지막 정리: 2026-10-24  
> 이 문서는 다른 기기에서 작업을 이어 갈 때 현재 상태와 다음 구현 순서를 확인하는 기준 문서다.

## 1. 제품의 현재 방향

수납바구니는 개인·가족·공동체가 함께 사용하는 수납 기록 서비스다. 한 사용자는 여러 Home에 참여할 수 있고, 각 Home 안에서 공간 트리와 물건을 관리한다.

```text
Home (공동체 또는 우리 집)
└─ 공간(Location)
   └─ 하위 공간(Location)
      └─ 물건(Item)
```

- `home_id`는 모든 데이터가 속하는 최상위 범위다. 회원가입하면 개인 Home 하나가 자동 생성된다.
- `parent_id`는 Home 안에서의 바로 위 공간을 뜻한다. `parent_id = null`은 Home 바로 아래 첫 공간이다.
- 공간은 다른 공간과 물건을 담는 계층이다. 물건은 한 공간에 보관되는 별도 데이터이며 좌표를 갖지 않는다.
- 화면에서 사용자에게 보이는 길이·좌표 단위는 항상 **cm**다. DB와 공간 계산에서는 **m**를 사용한다.

## 2. 완료된 구현

### Next.js 기반 전환

- 기존 Vite 프런트엔드와 Express 서버 구조를 정리하고, 단일 Next.js App Router 프로젝트를 만들었다.
- Next.js 16, TypeScript, React 19, ESLint, Tailwind 의존성이 설치되어 있다.
- 실행용 명령 파일을 루트에 뒀다.

```text
install.cmd  -- 의존성 설치
dev.cmd      -- 개발 서버 실행
build.cmd    -- 프로덕션 빌드 확인
lint.cmd     -- ESLint 확인
start.cmd    -- 빌드 후 프로덕션 실행
```

- 최근 `lint.cmd`, `build.cmd` 검증은 통과했다.

### 공개 소개와 인증

- `/` : 서비스 소개용 인트로 화면. 로그인하지 않아도 접근할 수 있다.
- `/login` : 이메일·비밀번호 로그인 화면.
- `/signup` : 표시 이름·이메일·비밀번호 회원가입 화면.
- `/auth/callback` : Supabase 이메일 인증 뒤 세션을 교환하는 경로.
- `/app/*` : 로그인 사용자만 접근 가능한 앱 영역. 로그인하지 않았다면 `/login`으로 이동한다.
- 아이콘은 `lucide-react`를 사용한다. 텍스트로 된 임시 Home 표기 대신 아이콘 중심으로 바꿨다.

현재 비밀번호 규칙은 8~72자, 표시 이름은 2~30자다. 이메일 형식과 필수값은 서버 액션에서 Zod로 다시 검증한다.

### Supabase 연결

- 새 Supabase 프로젝트에 초기 SQL 스키마를 실행했다.
- Supabase Auth URL 설정에 로컬 개발 주소와 `/auth/callback` 주소를 등록했다.
- `.env.local`에는 로컬 개발에 필요한 Supabase URL과 공개 키만 둔다. 이 파일은 Git에 포함하지 않는다.
- `profiles`, `homes`, `home_members`, `locations`, `items`, `activity_events`와 RLS 정책의 초기 구조가 준비되어 있다.
- 회원가입 시 프로필, 개인 Home, owner 멤버십을 만들도록 DB 트리거를 구성했다.

### 수납 지도 화면 샘플

현재 지도는 DB 데이터가 아닌 화면 동작을 검토하기 위한 샘플이다.

- `/app/space` : Home 전체 평면도 샘플.
- `/app/space/living-room` : 거실 내부.
- `/app/space/tv-cabinet` : TV장 내부.
- `/app/space/right-drawer` : 오른쪽 서랍 내부.
- Breadcrumb으로 상위 공간으로 돌아갈 수 있다.

사용 흐름은 한 화면에 모든 물건을 3D로 넣지 않고, 현재 공간의 바로 아래 자식만 보여 준 뒤 선택으로 들어가는 방식이다.

```text
집 전체 평면도
→ 거실·부엌·안방
→ TV장·수납장
→ 서랍·칸
→ 상자와 물건 목록
```

`three`, `@react-three/fiber`, `@react-three/drei`는 설치했다. 아직 실제 3D 장면은 만들지 않았고, 1·2계층은 평면도부터 구현한다.

### 등록 화면 샘플

- `/app/space/create` : 등록 방식 선택 화면.
- 공간과 물건을 먼저 구분한다.
- 공간은 `간편 등록`과 `지도 배치 등록`을 고를 수 있다.
- 지도 배치 등록은 `x, y, z, 너비, 높이, 깊이`를 모두 cm로 받는다.
- 물건 등록은 이름, 보관 공간, 수량만 받으며 좌표 입력은 없다.

현재 이 화면은 폼과 입력 흐름을 검토하는 단계다. 저장 버튼은 실제 Supabase에 아직 쓰지 않는다.

## 3. 확정된 데이터와 지도 규칙

### 논리 데이터와 시각 배치의 분리

```text
locations          공간의 이름과 부모-자식 관계
items              물건의 이름, 수량, 보관 공간
space_layouts      한 부모 공간을 바라보는 장면 설정
space_placements   그 장면 안에서 자식 공간이 보이는 좌표와 크기
```

`locations`에 좌표를 섞지 않는다. 예를 들어 거실은 Home 평면도에서는 방으로 보이고, 거실을 열면 그 장면에서는 TV장·수납장의 부모가 된다. 이때 자식이 부모 장면에서 어디에 보일지는 `space_placements`가 담당한다.

### 등록 방식

| 대상 | 필수 입력 | 추가 입력 |
| --- | --- | --- |
| 공간 간편 등록 | 이름, 부모 공간 | 없음 |
| 공간 지도 배치 등록 | 이름, 부모 공간 | x, y, z, 너비, 높이, 깊이, 표시 형태 |
| 물건 등록 | 이름, 보관 공간, 수량 | 없음 |

- 텍스트로 간편 등록한 공간도 나중에 지도에 배치할 수 있다.
- 지도 배치 공간 등록은 `locations`와 `space_placements`를 하나의 트랜잭션으로 만든다.
- 부모 공간이 존재해야만 자식 공간을 만들 수 있다.
- 다른 Home의 공간을 부모나 보관 위치로 사용할 수 없다.

### 공간 경계 검증

- 한 장면에 표시되는 형제 공간은 서로 겹칠 수 없다.
- 자식 공간은 부모의 모든 방향에서 최소 **1cm** 안쪽에 배치한다.
- 따라서 자식 최대 크기는 각 축에서 `부모 크기 - 2cm`다.
- x는 좌우, y는 높이, z는 앞뒤 축이다.
- 1·2계층은 x·z를 쓰는 위에서 본 평면도로 표시한다. 데이터는 처음부터 y·높이·깊이도 저장한다.
- 3계층부터 수납장·서랍 내부를 입체로 보여 줄 때 y·높이·깊이를 사용한다.

공간 생성·이동·크기 변경 때 서버는 아래를 모두 검사해야 한다.

```text
부모 경계와 1cm 여백 확인
→ 같은 장면의 형제 겹침 확인
→ 부모 축소 시 모든 자식이 남는지 확인
→ 조상 경계까지 확인
→ 모두 통과한 경우만 저장 및 기록 생성
```

검사 실패 시 자동으로 부모를 늘리지 않는다. 현재 부모 크기와 필요한 최소 크기를 cm로 알려 주고, 사용자가 부모를 수정하거나 다른 자식을 옮기게 한다.

## 4. 기록, 삭제, 권한 원칙

- 위치·물건 변경 이력의 원본은 `activity_events` 한 테이블이다.
- 물건 상세, 공간 상세, Home 전체 아카이브는 같은 이벤트 원본을 각 조건으로 조회한다.
- 이벤트에는 변경 전후 스냅샷과 `operation_id`를 남긴다.
- 위치 삭제처럼 물건 이동과 삭제가 함께 일어나는 작업은 같은 `operation_id`를 쓴다.
- 위치와 물건은 즉시 행을 지우지 않고 소프트 삭제를 사용한다.
- 위치 삭제 전 해당 위치의 물건을 다른 공간에 배정해야 한다.
- 여러 행을 바꾸는 작업은 브라우저에서 순서대로 처리하지 않고 Supabase PostgreSQL RPC 트랜잭션에서 원자적으로 처리한다.
- RLS는 현재 사용자가 member인 Home 데이터만 읽고 바꾸게 한다. 클라이언트는 `activity_events`를 직접 쓰지 않는다.

## 5. 아직 구현하지 않은 예정 작업

### 다음 우선순위: 실제 공간 등록 연결

1. 두 번째 SQL migration으로 `space_layouts`, `space_placements`를 추가한다.
2. 공간 간편 등록, 공간 지도 배치 등록을 처리하는 PostgreSQL RPC를 만든다.
3. RPC에서 Home 멤버 권한, 부모 관계, m 변환, 여백, 겹침을 한 번에 검증한다.
4. 성공 시 공간/배치/활동 기록을 같은 트랜잭션으로 저장한다.
5. `/app/space/create` 폼을 실제 DB의 Home·부모 공간 목록과 연결한다.
6. `/app/space`와 하위 지도 화면을 샘플 데이터가 아니라 DB 데이터로 바꾼다.

### 이어서 만들 기능

- 공간 이름 수정, 부모 이동, 지도 배치 수정, 부모 축소 검증.
- 물건 실제 CRUD와 공간 선택 목록.
- 위치 삭제 전 물건을 새 위치로 배정하는 화면과 RPC.
- 공간별 기록, 물건별 기록, Home 전체 아카이브.
- Home 전환, 구성원 목록과 권한 관리.
- owner가 초대 코드를 만들고 폐기하는 기능.
- 회원가입 중 초대 코드 입력 → Home 이름과 대표자 마스킹 확인 → 참여/개인 Home 선택 흐름.
- 검색 결과에 전체 경로 표시. 예: `우리 집 > 거실 > TV장 > 오른쪽 서랍`.
- 3계층 이상 공간의 실제 Three.js 입체 장면.

## 6. 배포와 다른 기기에서 이어 하기

최종 배포 구조는 아래로 정했다.

```text
GitHub (소스와 Git 이력)
→ Vercel (Next.js 화면과 서버 기능)
→ Supabase (Auth, PostgreSQL, RLS)
```

Render는 Next.js 전환 뒤 더 이상 필요하지 않으며, 예전 Render 서비스는 최종 Vercel 검증 후 삭제하는 방향이다.

다른 기기에서 이어 할 때는 GitHub에서 최신 소스를 가져온다.

```cmd
git clone https://github.com/2hyun2/storage-basket.git
cd storage-basket
install.cmd
```

그 다음 새 기기에서 `.env.local`을 만들고 Supabase 프로젝트의 공개 URL과 공개 키를 넣는다. `.env.local`은 GitHub에 올리지 않는다. 개발 서버는 `dev.cmd`로 실행한다.

현재 Next.js 전환 파일은 아직 GitHub 원격 저장소에 push하지 않았다. 원격 저장소에는 이전 Vite/Express 버전이 남아 있으므로, 이 전환 작업을 커밋·push하기 전에는 변경 내용을 다시 검토해야 한다.

## 7. 확인이 필요한 결정

- 실제 지도용 `space_layouts`의 장면 종류를 첫 migration에서 enum으로 고정할지, 문자열로 유연하게 둘지.
- Home 전체 평면도 크기를 고정 캔버스로 시작할지, owner가 cm 단위로 편집할 수 있게 할지.
- 초대 코드의 만료 기간과 최대 사용 횟수 기본값.
- 물건의 단위, 분류, 태그, 사진 첨부를 어느 시점에 1차 기능으로 넣을지.
